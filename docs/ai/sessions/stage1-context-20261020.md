# 第 1 阶段：语境装配（stage1-context-20261020）

## 目的 / 结论 / 依据

- **目的**：读取作业 PDF，对齐需求理解，暴露歧义，不产出任何代码。
- **结论**：本项目是「内部可靠通知投递服务」——业务系统提交外部 HTTP 通知请求，本服务异步、可靠地投递到供应商 API。MVP 核心为：接收 API + SQLite 持久化 + 后台线程 worker 指数退避重试，投递语义为至少一次。
- **依据**：作业原文「需求描述」「设计说明要求」「评估重点」三节；AGENTS.md 复杂度克制原则。

## 作业要点摘录

- 评估重点：工程判断与取舍逻辑，非功能齐全度。
- 必须回答三个设计问题：①系统边界（解决什么/明确不解决什么）②投递语义与长期失败策略 ③拒绝了 AI 的哪些「过度」建议 + 未来演进路径。
- 业务方不关心外部 API 返回值，只要求稳定可靠送达。
- 不同供应商 URL / Header / Body 格式不同。
- 交付物：设计文档、MVP 代码、AI 会话记录 zip（`make sessions`）。

## 我的理解（推断，待实现期验证）

1. 业务系统 → 本服务 API（提交通知）→ 持久化 → worker 异步投递 → 失败重试（指数退避）→ 超过上限标记失败。
2. 至少一次语义；下游幂等性由下游负责，文档中声明而非系统内解决。
3. 供应商差异第一版用朴素方式表达（请求模板随任务提交），不引入插件/适配器体系。
4. 明确不做：多租户、优先级队列、控制台、鉴权、复杂路由。

## 人类决策记录

- **技术栈**：FastAPI + SQLite + 线程 worker（人类确认）。放弃纯标准库方案：HTTP 服务与并发管理用纯标准库代码繁琐冗长，FastAPI 一个依赖换来显著可读性收益；放弃消息队列：当前规模下 SQLite 轮询足够，队列属于未被论证的基础设施。
  - 澄清：第三方依赖仅 FastAPI + uvicorn；worker 用的 `threading` / `sqlite3` 均为标准库。
  - 为什么 worker 用线程轮询而非消息队列：线程方案的失败模式最简单——出问题看日志看表即可理解全部状态，崩溃重启任务仍在表里。对比 asyncio：投递吞吐为个位数/秒，异步收益为零且与同步 SQLite 驱动混用易阻塞事件循环；对比 celery/RQ：多一个 broker 常驻组件，失败模式翻倍。**每个组件的失败模式都必须是一个人能完全理解的——「可靠」的前提是「可推理」。**
  - 轮询与推送的辨析（人类追问）：SQLite 没有任何变更主动通知机制（已验证事实），worker 只能轮询 `status='pending'` 的任务。轮询的真实代价不是性能（带索引的空查询为微秒级，1 秒一次≈零负载），而是投递延迟上限（平均半个轮询间隔，≈0.5s，对本业务无感）与空转。SQLite 的 `update_hook` 仅同进程触发、跨连接不可靠，不采用。
- **SQLite 的适用边界与演进触发条件**（人类质疑「上亿/几十亿条消息」后确认）：
  - 该质疑成立，结论边界被修正为：**SQLite 方案适用于存量百万级、活跃任务万级以下、写入每秒百次以内**。超过任一指标即触发迁移。
  - 量级推演（基于 SQLite 已知特性的推断，非实测）：10 亿行 ≈ 500 GB 表，SQLite 定位为 GB 级存储方案，且全库单写锁会使 API 写入与 worker 状态更新互相阻塞——**先崩的是写入吞吐，不是轮询查询**（带部分索引的轮询只扫活跃任务，微秒级不变）。
  - 演进路径：`SQLite 轮询 → PostgreSQL（分区表 + LISTEN/NOTIFY 原生推送，轮询消失）→ 消息队列 + 独立投递集群（解决多机分发/背压/死信）`。每级演进有明确触发条件，任务表数据模型到 PG 近乎原样迁移，store 层隔离，换存储只动一个模块——起步选择不构成沉没成本。
  - 为什么不为几十亿量级现在就设计：那需要存储分片、投递集群、背压、死信处理整套重新设计，为一个概率性未来预付全部成本是更贵的错误；且业务形态（广告回调/CRM/库存通知）基于需求原文推断天然到不了该量级。**不预测流量，但必须预先写明每个组件的失效边界和触发动作——知道自己什么时候错，比永远正确更可行。**
  - 人类补充要求（已验证事实）：必须在设计文档中明确写入「业务增长带来的连锁影响」评估——本选型仅在小业务量下无问题，后续增长会影响写入吞吐、表体积、投递延迟、运维方式，演进方案与触发指标需作为设计文档的一等公民章节，而非事后补充。
- **鉴权**：第一版不做，在文档中声明为「明确不解决的问题」（人类确认）。

## 被驳回的提案记录（人类提出 → AI 反驳 → 人类认可驳回）

- **提案：引入 Redis 充当消息队列**（人类提出）。理由：推模式省去轮询，「不用系统承担过多职责」。
- **反驳要点**（AI 独立分析，人类最终认可）：
  1. Redis 作可靠队列需自建 ack 协议（`BLMOVE` processing 队列 + 超时回收 + `LREM`），且无原生延迟队列（需 ZSET 自造），调度代码量反而超过 SQLite 轮询循环；新增 Redis 进程挂掉 / AOF 丢尾 / 内存淘汰误杀等失败模式。
  2. 职责分离（SRP）准确含义是「一个模块只因一个理由变化」，已在代码模块层（api/ 与 worker/ 隔离）实现，无需用基础设施进程表达；「存储即队列」使受理+入队为一个本地事务，原子性免费。
  3. 引入 MQ 反而使事务管理变重：DB+MQ 双写无法用单事务覆盖，须引入 Transactional Outbox（本地事务 + outbox 表 + relay 轮询器 + 幂等消费）——**绕一圈重新发明轮询，还多付一个常驻依赖**。
  4. 反对「后期都要加上，不如现在加」：不是所有系统都会长到需要 MQ；store 层隔离使未来迁移成本≈换一个模块实现，现在加是纯预支运营成本。加 MQ 的最佳时机是触发条件出现时。
- **人类最终结论**（2026-10-20）：认可驳回。小数据量级采用 SQLite + worker 轮询推送；MQ 演进不在 stage1 完成，留待后续论证环节。
- **改判条件**（保留）：若组织已有 MQ 平台/专人运维，或本服务未来承接多业务线共享事件流，引入 MQ 的边际成本骤降，结论可翻转——判断依据是组织现实而非技术美感。
