分两部分解释选型逻辑：

## 1. 为什么是 FastAPI + SQLite（而不是别的）

| 候选 | 被放弃的原因 |
|---|---|
| 纯标准库 `http.server` | 需要手写路由解析、请求校验、JSON schema 校验，代码冗长且容易出 bug——省一个依赖，换来的是更多自造轮子，违背「克制复杂度」的本意 |
| Flask | 也能做，但请求体校验要靠手写或 pydantic（又得加依赖）；FastAPI 自带 pydantic 校验 + 自动生成 OpenAPI 文档——而本作业恰好需要交付 `contracts/openapi.yaml`，工具链天然契合 |
| 消息队列（RabbitMQ/Redis） | 作业明确允许用，但当前规模下这就是**未被论证的基础设施**：多一个常驻中间件、多一种部署失败模式、多一套运维知识。SQLite 一张表就是我们的队列，`status` 字段 + 轮询就是消费者 |
| PostgreSQL | 与 SQLite 相比，MVP 阶段没有并发写压力、没有多机部署需求，PG 带来的唯一收益是「未来不用换」——为假设的未来付费，不做 |

**SQLite 被选中的核心论据**：它是唯一一个「既是持久化存储、又天然提供事务原子性（取任务/标记失败不会出现竞态）」的零运维选项。断电重启后任务不丢——这直接服务于「可靠投递」这个核心需求。

## 2. 为什么 worker 用「线程 + 轮询」这种朴素实现

这个选择的关键论据是**失败模式简单**：

- **线程方案**：`while True: 从 SQLite 取一条 pending 且到期的任务 → HTTP POST → 按结果更新状态 → sleep 退避`。出问题时，你看日志、看表，就能理解全部状态。崩溃了重启进程即可，任务还在表里。
- **对比 asyncio 方案**：性能更好（IO 密集场景），但异步代码 + SQLite 的同步驱动混用是著名的坑（阻塞事件循环），调试难度显著上升。MVP 的投递吞吐是每秒个位数级别，asyncio 的收益为零。
- **对比 celery/RQ + 独立 worker 进程**：又引入一个中间件 + 一个 broker，失败模式翻倍（broker 挂了怎么办？worker 和 API 版本不一致怎么办？）——这正是作业里「识别并主动管理复杂度」想考察的反面教材。

**放弃线程方案会失去什么**：单进程吞吐上限低（一个 worker 线程串行投递）、多线程写 SQLite 需要注意锁。这些在当前规模（内部通知，非高并发）都不是真实约束。如果未来流量涨了，演进路径是清晰的：加 worker 线程数 → 换 PostgreSQL → 再不行才换消息队列。**每一级演进都有触发条件，而不是现在预支。**

一句话总结：这套选型的原则是——**每个组件的失败模式都必须是我一个人能完全理解的**。这比性能、比可扩展性都重要，因为「可靠」的前提是「可推理」。

你的理解完全正确，先给结论：**SQLite 没有任何主动通知机制，它就是一张表，worker 只能靠轮询查询**。它不是消息队列，我们只是在用它模拟队列的行为。区别在哪、为什么这里够用，我拆开讲。

## 1. 消息队列 vs 我们的表轮询，本质差异

```
真 MQ（RabbitMQ）：  生产者投递 → broker 主动推给消费者 → 消费者阻塞等待，零空转
SQLite 轮询：        worker 每隔 N 秒执行一次 SELECT ... WHERE status='pending' → 大部分查询扑空
```

消息队列的核心增值就是「推」——消费者挂起等待，事件来了被唤醒。我们的方案是 worker 醒着但反复问「有活吗？没活。有活吗？没活」。

**已验证的事实**：SQLite 官方没有变更推送/订阅机制（3.x 全系）。想近似「主动通知」只有两条路，我都不推荐：
- SQLite 的 `update_hook` C 回调——只在**同一进程内**的写操作触发，而且我们 API 进程写、worker 进程（或线程）读，跨连接不可靠，属于冷门 API；
- 单独起一个「监听进程」——监听本身还是轮询，只是把轮询挪了个位置，没有解决问题。

## 2. 那轮询的代价到底多大？

轮询的开销 = 空查询频率 × 单次查询成本。我们来算真实数字（基于 SQLite 已知特性的推断，非实测）：

- 单次空查询：一条带索引的 `SELECT ... WHERE status='pending' AND next_attempt_at <= now LIMIT 1`，在万级记录的表上是**微秒级**，不产生磁盘 IO（索引页在内存里）
- worker 每 1 秒轮询一次 = 每秒一次微秒级查询
- 这个负载对 SQLite 来说约等于零

所以真正的回答是：**性能不会出差错，因为轮询的开销根本不在「性能敏感」的量级上**。轮询的真实缺点不是慢，而是两点：

1. **延迟上限**：任务从提交到被投递，平均多等半个轮询间隔。1 秒轮询 = 平均 0.5 秒额外延迟。对「通知广告系统/CRM」这种业务，0.5 秒完全无感。
2. **空转**：浪费的是 CPU 周期，但量级小到可以忽略。

## 3. 什么时候这个判断会失效（演进触发条件）

我会把这条写进设计文档，作为「何时必须换 MQ」的量化标准：

- 轮询延迟不可接受（业务要求提交后 <100ms 投出）→ 换推模式
- 表写入速率高到 SQLite 写锁成为瓶颈（SQLite 全库单写锁，大致在每秒数千次写以上才开始疼）→ 换 PostgreSQL，此时顺手可以用 PG 的 `LISTEN/NOTIFY` 拿到真正的推送语义
- 需要多个独立服务消费同一事件流 → 这才是消息队列的真正适用场景

**放弃推模式我放弃了什么**：投递延迟从毫秒级退到亚秒级、系统少了「事件驱动」的优雅。换来的是：零中间件、崩溃重启后状态天然一致（表就是真相）、整个投递逻辑 100 行以内可读完。在 MVP 阶段，我认为这笔交易非常划算。

一句话：**轮询不是妥协的将就，而是这个规模下的正确答案**——消息队列解决的是「高吞吐 + 低延迟 + 多消费者」三个问题，我们当前一个问题都没有。

## 1. 几十亿条时，真正的账是什么样

先纠正一个容易误判的点：**在那个量级下，轮询开销反而是最小的问题**。按一条通知任务约 500 字节算：

| 量级 | 表体积 | 发生了什么 |
|---|---|---|
| 10 亿行 | ~500 GB | SQLite 官方定位就不适合了（其推荐场景是 GB 级）；索引 B 树 4~5 层，单次查询可能多次磁盘 IO；**全库单写锁**——API 写入和 worker 更新状态开始互相阻塞，写入吞吐先崩 |
| 100 亿行 | ~5 TB | 单机文件系统都吃力，谈轮询已经没有意义 |

也就是说：**几十亿行时第一个死掉的不是轮询，是 SQLite 本身**。轮询查询因为有 `status` 部分索引，只扫 pending 那一小撮（活跃任务通常远小于存量），空查询依然是微秒级——但写入吞吐、锁竞争、文件体积会先把这个方案压垮。

正确的演进路径在那个量级是：

```
SQLite 轮询 → PostgreSQL（分区表 + LISTEN/NOTIFY 推送）→ 真消息队列 + 独立投递集群
```

到第二级时，`LISTEN/NOTIFY` 顺带解决了你上一个问题里的「主动通知」——PG 原生支持推送，轮询消失。到第三级才轮到 Kafka/RabbitMQ 登场，那时它们要解决的是多机投递集群的任务分发，而不是「避免轮询」。

## 2. 那为什么第一版仍然用 SQLite？——工程判断的核心

**不是因为我们赌业务永远到不了几十亿，而是因为为一个概率性未来预付全部成本，是更贵的错误。**

假设现在就直接上 Kafka + PG 分区集群：

- 部署复杂度：3 个常驻组件起步，每个都有自己的故障模式
- 交付时间：MVP 周期可能翻数倍
- 而它防的那个场景（日投递量上亿）在作业描述里是「企业内部关键事件通知」——广告回调、CRM 状态变更、库存变更，这个业务形态**天然到不了**几十亿量级（基于需求原文的推断）

更关键的一点：**从 SQLite 起步并不浪费**。数据模型（任务表）到 PG 几乎原样迁移，业务代码里 store 层是隔离的，换存储只动一个模块。这是「演进式设计」——让架构对扩展友好，而不是现在就实施扩展。

你的质疑让我把结论表述得更精确了，这句话应该写进设计文档：

## 1. Redis 当队列，真实要付的账

我们的核心需求是「**可靠**投递」，这意味着队列必须回答：消费者取走一条消息后进程崩了，这条消息去哪了？

| 问题 | SQLite 表方案 | Redis List 方案 |
|---|---|---|
| worker 取出任务后崩溃，任务会不会丢？ | 不会——任务还在表里，状态没变，重启继续投 | **会丢**。`LPOP` 取出即从队列消失。要补这个洞得用 `BLMOVE` 塞进 processing 备份队列 + 超时回收逻辑 |

关键反直觉点：**Redis 队列「可靠模式」的代码量，比 SQLite 轮询循环还多**。GitHub 上大量「Redis 任务队列」库（如 RQ、celery 的 Redis broker）存在的意义，就是把上面那套 ack/备份/回收逻辑封装起来——用它们等于引入库，裸写等于自造轮子。两条路都比我们的方案重。

## 一次投递在网络上发生了什么

worker 调用供应商 API 时，一次 HTTP 请求分两个阶段，每阶段各有一个「最多等多久」：

```
worker                     网络                      供应商服务器
  │                                                  │
  │──── ① 建立连接 (TCP 握手 + TLS) ────────────────→│
  │     连接超时 = 5s                                │
  │     「5 秒内连不上对方，放弃」                     │
  │                                                  │
  │──── ② 发送请求体 ───────────────────────────────→│
  │                                                  │
  │←─────────── ③ 等对方处理并返回响应 ──────────────│
  │     读超时 = 10s                                 │
  │     「发出去之后 10 秒内收不到响应，放弃」          │
```

**连接超时（5s）**：管的是「电话打通没」。对方服务器宕机、域名解析失败、网络不通——都是这个阶段卡住。正常建连是几百毫秒，5 秒还连不上基本就是对方没了。

**读超时（10s）**：管的是「打通了电话，对方多久给答复」。请求已经发过去了，对方收到了、正在处理，但迟迟不返回响应。

## 为什么必须有这两个上限

如果不设上限，worker 的默认行为是**无限等待**——对方服务器卡死了，我们这个投递线程就永远挂在那里。而 MVP 里 worker 线程数量是有限的（比如 4 个），挂 4 个线程 = 整个投递系统停摆。所以超时本质上是在保护**我们自己的可用性**，不只是「嫌对方慢」。

## 超时之后发生什么

超时被归类为「失败」的一种（和 5xx 同类），走第 3 点的重试流程：30 秒后重试 → 指数退避 → 直到用完 7 次机会标记 `dead`。

一个值得注意的细节：**读超时放弃时，我们的请求其实可能已经到达对方、甚至对方已经处理完了**——只是响应没来得及回来。这正是「至少一次」语义的来源之一：重试可能导致对方收到两次，所以下游必须幂等（这条已写进 stage1 的理解清单）。超时是「不知道成没成功」的典型场景，比明确的 4xx 更危险，这也是为什么 4xx 直接判死、而超时要重试。

```
第 5 次失败 → 等 8min

总跨度：30s+1m+2m+4m+8m+16m ≈ 31.5 分钟，加上最后一次投递本身，覆盖约 1 小时窗口
```

## base=30s 怎么想的

base 回答的问题是：「**第一次重试前，给对方多久的喘息时间？**」

- 太短（如 1s）：供应商最常见的故障是「发布重启，30 秒恢复」。1 秒后重试，撞在同一口钟上，浪费一次机会还加重对方负担。
- 太长（如 10min）：大多数故障远在几分钟内就恢复了，白白把通知延迟拉长 10 倍。
- 30s 的含义：比「进程重启级故障」的典型恢复时间略长，又能让瞬时抖动类故障（网络闪断、超时）在半分钟内完成第一次补救。这是 webhook 生态的常见量级（基于惯例的推断，非实测数据）。

## factor=2 怎么想的

factor 回答的问题是：「**每多失败一次，说明故障更深，应该加倍还是线性地等更久？**」

- 线性（factor=1，等差 30s/30s/30s…）：7 次只覆盖 3.5 分钟——对「供应商停机维护半小时」的场景，第 4 次就烧完了所有机会。
- factor=3：覆盖时间更长，但后期间隔膨胀太快（30s→13.5min→40min），单次故障的尾部等待过久。
- factor=2 是折中：**前密后疏**——前期快速试掉瞬时故障（最常见），后期拉开间隔省着试长期故障（较少见），同时把总窗口推到小时级。这也是业界重试库的默认值（如 AWS SDK、Google SRE 手册推荐形态），选它不是创新，是「不发明新轮子」。

## 两个隐含的诚实声明

1. **这些值没有经过本系统真实流量的验证**——MVP 阶段不存在「实测调优」，值是否合适要等上线后看 dead 任务的失败原因分布。所以我把它们放进配置文件（`retry_base_seconds=30, retry_factor=2, max_attempts=7`），改值不改代码。
2. 行业里标准做法还会加 **jitter（随机抖动）**——比如等 30s ± 随机 20%，防止成百上千个任务在同一秒集体重试、把恢复中的供应商再打趴下（「惊群」）。**我第一版不做它**：当前是单 worker 串行投递，物理上不会同时打出多个请求，jitter 解决的问题不存在。但它会写进「未来演进」清单——当 worker 并发数上去之后，jitter 从可选项变成必选项。

## 原文的精确含义

```
业务系统 ──提交通知──→ 我们的服务 ──HTTP 请求──→ 供应商 API
                        ↑
              「不关心返回值」豁免的是左边这位
              但「确保可靠送达」的责任落在了我们头上
```

**「可靠送达」恰恰必须依赖返回值才能判定。** HTTP 协议里，一次请求必然有结果，只有四种可能：

1. 对方返回 200/201/204 等 2xx → 对方明确说「收到了」→ 这才叫「送达」
2. 对方返回 500 → 对方明确说「我收到了但处理失败」→ 没送达
3. 超时/连接失败 → 对方什么都没说 → 不知道，按未送达处理
4. 对方返回 400 → 对方说「你这请求本身是错的」→ 没送达

如果我们的服务也不看返回值，那「发出去」和「送到了」就无法区分——发出去了就算完成？那这个系统和 `curl` 脚本没区别，作业题里的「可靠」二字就无从谈起。

## 换句话说

需求这句话其实是在**定义系统边界**：返回值的「读取」和「处理」职责被从业务系统身上剥离，**转移给了我们**。业务方只管把请求内容交给我们，返回值的判断、失败后的重试、长期不可用的处理，全是我们的职责——这正是这个系统存在的理由。

我们看返回值，但只看状态码这一层——**不解析响应体**（body 里的业务含义，业务方不关心，我们也不关心，读了没用，还多一层解析失败的风险）。所以第 1 点的完整表述是：

## 一、架构

```
┌─────────────────────── 单进程 (uvicorn) ───────────────────────┐
│                                                                │
│  FastAPI (api/)          SQLite (store/)         worker 线程    │
│  POST /notifications ──→ tasks 表 ←──────────────  轮询循环      │
│  GET  /tasks/{id}                            │        │         │
│  GET  /tasks?status=dead                     │        ▼         │
│                                              │   HTTP → 供应商   │
└────────────────────────────────────────────────────────────────┘
```

**关键决策：worker 和 API 同进程**，不开独立 worker 进程。依据：MVP 部署复杂度减半（一条 `make run` 起全套）；SQLite 同进程读写无跨进程锁问题。**放弃独立进程的代价**：投递负载和 API 负载共享 CPU——当前量级无影响；若未来分离，代码上 worker 本就是独立模块，拆出去只是改启动方式。

## 二、数据模型（草案，stage4 冻结为 schema.sql）

```sql
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,              -- uuid4
    url TEXT NOT NULL,
    method TEXT NOT NULL DEFAULT 'POST',
    headers_json TEXT NOT NULL,       -- 最终形态，服务端不解释
    body TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',   -- pending|delivering|retrying|done|dead
    attempts INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TEXT NOT NULL,    -- ISO8601，轮询按此索引
    idempotency_key TEXT UNIQUE,      -- 可空
    last_error TEXT,                  -- 最近失败原因（状态码/超时类型）
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX idx_tasks_due ON tasks(status, next_attempt_at);
```

`attempts` + `next_attempt_at` 两个时间字段合并在一行内表达全部重试状态，无需独立的重试历史表。**放弃重试历史表**：每次失败信息覆盖写入 `last_error`，只留最近一次——完整历史对 MVP 排障没有增量价值，日志文件里有。

## 三、worker 主循环（伪码）

```
loop:
  task = SELECT * FROM tasks
         WHERE status IN ('pending','retrying') AND next_attempt_at <= now
         ORDER BY next_attempt_at LIMIT 1
  if task:
    UPDATE status='delivering'        -- 抢占标记，防未来多 worker 重复投
    result = http.request(task, timeout=(5,10))
    2xx      → status='done'
    4xx      → status='dead', last_error=状态码
    5xx/超时/连接错 → attempts+=1
                  attempts < 7 → status='retrying', next_attempt_at=now+30s*2^n
                  else         → status='dead'
  else:
    sleep(1s)
```

**崩溃恢复**：启动时执行一条 `UPDATE tasks SET status='retrying', next_attempt_at=now WHERE status='delivering'`——把上次崩溃时卡在投递中的任务放回重试。就一条语句，没有恢复框架。

## 3. Webhook 事件订阅 —— 理解错位，方案不变，我解释清楚

你描述的逻辑——「业务方主动推送 → 写入我们的 tasks 表」——**恰恰就是我们正在建的**，这个没有分歧。被砍掉的是另一种架构，区别在「业务方的推送动作从哪来」：

```
我们建的（拉/推皆可，业务方代码显式调用）：
  业务代码执行完「注册成功」逻辑 → 代码里调 client.submit(...) → 进 tasks 表
  ※ 业务方在自己的代码里明确地「发起」通知

被砍掉的（事件订阅模型）：
  业务系统把「注册成功」发到内部事件总线 → 我们订阅这个事件 → 自动生成通知任务
  ※ 业务方不写任何调用代码，我们被动感知他们的事件
```

后者的隐含前提是**公司存在统一的事件总线**（MQ/事件中心），我们接入并订阅各业务系统的事件流。如果存在，我们的「受理 API」会被事件消费器替代——这是 stage1 里「MQ 改判条件」的同族问题。作业需求写的是「业务系统调用外部 API 进行通知」，主语动作是「调用」，所以我判断是前者。**如果实际语境是后者（有事件总线），这一条要翻案**——请确认你理解的业务方接入方式是哪种。

## 4. 优雅停机 —— 细化版

```
SIGTERM 到达后的时序：

t=0    worker 收到 stop 信号
t=0    worker 停止领取新任务（标志位，主循环每轮检查）
t=0    若正在投递：不打断当前 HTTP 请求，等它自然结束
        ├─ 结束前 uvicorn 给 worker 的宽限期：15s（> 读超时 10s，
        │   保证任何进行中的投递必然在这一窗口内落地）
t≤15s  当前任务按结果正常落库（done/retrying/dead）
t≤15s  uvicorn 关闭 API，进程退出

异常路径：
超过 15s 仍没结束（理论上只有网络栈卡死才会发生）
        → 进程强退，该任务留在 delivering 状态
        → 下次启动的崩溃恢复语句把它放回 retrying
        → 代价：对方可能收到重复投递（至少一次语义的既有代价，无新增）
```

**为什么完整 drain（等队列清空再退）是过度**：停止服务时队列里可能有几百个 pending 任务，drain 意味着停机时间不可控（和重试队列长度成正比）。而「停机期间 pending 任务无人投递」本来就不构成损失——它们就在表里，重启后继续。**drain 唯一真正的保护对象是 delivering 中的那一个任务**，上面的 15s 宽限 + 崩溃恢复兜底已经覆盖它。这就是「完整 drain 95% 的复杂度在保护不重要的东西」的判断依据。

## 场景设定

广告系统 A 的契约（vendors 表里的一行）：

```json
{
  "vendor_id": "ads-a",
  "url_template": "https://ads-a.com/api/callback",
  "body_template": "{\"user_id\": \"{{user_id}}\", \"channel\": \"{{channel}}\"}"
}
```

现在业务方提交：`vendor_id=ads-a`，变量 `{"user_id": "123", "channel": "tiktok"}`。

## 两种渲染时机

**方案 A：受理时渲染快照（我的提议）**

```
t1  提交到达 → 服务端立刻用当前契约渲染：
    body = {"user_id": "123", "channel": "tiktok"}
    → 渲染结果作为最终形态写进 tasks 表
t2  （10 分钟后）运维把 ads-a 契约的 url 改成了新地址
t3  worker 投递 → 用的是 t1 存下的快照 → 发到旧地址
```

**方案 B：投递时渲染（另一种做法）**

```
t1  提交到达 → tasks 表只存 vendor_id + 原始变量
t2  （10 分钟后）契约被改成新地址
t3  worker 投递 → 此刻才读契约渲染 → 发到新地址
```

## 为什么我提议 A

1. **可复现性（运维视角）**：方案 A 下，tasks 表里每一行都是「这个任务到底发了什么字节」的完整证据，排查「对方说没收到/收到的内容不对」时无需反推「当时契约长什么样」。方案 B 里，表里只有变量，最终内容取决于投递那一刻的契约——事后无法重建现场。
2. **失败归因稳定**：方案 B 下，一次投递失败的原因可能是「变量缺失」，也可能是「契约在我排队期间被改坏了」——两种失败的处理人不同（业务方 vs 运维），混在一起会互相甩锅。方案 A 把模板错误全部拦在受理时刻（提交时校验，缺变量直接 400 打回），进队列的任务必然是渲染成功的。
3. **worker 更简单**：worker 只做「取最终形态 → 发 HTTP」，不碰模板逻辑。渲染逻辑只存在于 API 受理一处。

## 方案 A 放弃了什么（诚实声明）

- **排队中的任务吃不到契约热更新**。如果「改契约」的动机是修 bug（比如 url 写错了），方案 B 能让积压任务立刻走新契约，方案 A 需要把受影响的 pending 任务作废重提。我的判断：契约变更应当是低频、审慎的操作（它改变对外行为），为此付出快照的代价值得；如果未来出现「高频调契约」的真实需求，那是重新评估的信号，不是现在就该支持的能力。
- **tasks 表体积变大**：存渲染后全文 vs 只存变量，每行多几百字节。在百万级存量表上可接受（属于 stage1 划定的边界内）。

一句话总结：**快照 = 受理那一刻把「契约 × 变量」压成一个不可变的最终请求存档，此后契约怎么改都与在途任务无关**。它用一张更大的表，换来了每次投递的完整可追溯性。

## 对策：不换方案，补一个「契约变更动作」

```
改契约的标准流程（写成一条命令或 API 动作）：
  1. PUT /vendors/ads-a          （更新契约）
  2. POST /vendors/ads-a/rerender （新增，一行 UPDATE + 重新渲染）
     → 把该 vendor 下所有 status IN ('pending','retrying') 的任务
       用新契约重新渲染、重置 next_attempt_at
  3. dead 任务不自动复活——它们需要业务方确认后重提
     （自动复活等于掩盖了「为什么死」的调查，也违背最少惊讶）
```

这个 rerender 动作大约 10 行代码，但它同时解决了：
- 你担心的「改地址后 pending 任务投旧地址」→ 立刻跟上新契约
- 方案 B 想要的热更新收益 → 以**显式、留痕**的方式获得，而不是隐式混入投递
- 可追溯性不丢 → rerender 前后 attempts 历史完整保留，谁在何时刷新过任务有记录

## 一、架构


**契约变更语义**（经你确认的三句话）：

## 三、投递语义（stage2 定点，对抗中未变）

- 2xx=送达；不跟随 3xx；响应体不读取不存储
- 4xx → 直接 dead；5xx/超时/连接错 → 重试
- 指数退避 base=30s、factor=2、最多 7 次尝试（窗口约 1 小时），参数走配置；jitter 暂不做（单 worker 无惊群），并发化后必选
- HTTP 超时：连接 5s + 读 10s
- 状态机 `pending → delivering → done / retrying → dead`

## 四、优雅停机（细化版）

SIGTERM → worker 停止领新任务 → 在途投递等它自然结束（宽限 15s > 读超时 10s）→ 正常落库退出。超时强退的残留 delivering 由崩溃恢复兜底，重复投递是至少一次的既有代价，无新增。**完整 drain（清空队列再退）明确不做**——它 95% 的复杂度在保护不重要的 pending 任务。

## 缺陷详解：UNIQUE 全局约束 vs 时间窗口语义的冲突

### 三个前提叠在一起才暴露

1. **schema 的物理约束**（冻结契约）：`idempotency_key TEXT UNIQUE` ——整张表里，这个字段的值不允许出现两次。这是**不带任何时间条件的**、永久生效的数据库层约束。
2. **业务语义**（stage2 定点 7）：幂等保护只在 **24h 窗口内**有效——「24h 内相同 key 返回首次 task_id」，言外之意是 24h 之后，同一个 key 提交应该被当作**新请求**正常受理（调用方可能就是想再发一次同样的通知，比如一个月后给同一个用户再发一次注册回调）。
3. **代码的判定逻辑**：受理时查 `WHERE idempotency_key=? AND created_at>=24h前`，查到 → 返回旧任务；查不到 → 插入新行。

### 冲突爆发的时序

```
第 0 小时：key="order-001" 的任务 A 入队（UNIQUE 槽位被 A 占据）
第 25 小时：业务方再次提交 key="order-001"
            → 代码查窗口内：没有（A 已 25h，超出窗口）→ 走插入分支
            → INSERT 触发 UNIQUE 约束 → IntegrityError 崩溃！
```

也就是说：**代码认为「可以新建」，数据库认为「不允许新建」**，两个判定者用了不同的规则（代码带时间条件，数据库不带）。窗口内一切正常，冲突只在「跨窗口的重复 key」这一种场景爆发——这正是测试最容易漏掉的那类 bug：主路径全绿，边界路径崩溃。

### 两种修法的取舍

| 修法 | 做法 | 后果 |
|---|---|---|
| ~~DELETE 旧行~~ | 插入前删掉窗口外的同 key 旧任务 | 释放了 key，但**旧行连同它的 attempts 投递历史一起被删**——如果那条旧任务曾投递失败、运维还没排查，证据就没了。直接违背你在 stage3 驳回我的理由（「没有完整历史排查表就很难观测问题」）——我等于用你刚纠正过我的方式又犯了一次错，写完就自我否决了 |
| ✅ key 加后缀 | `UPDATE 旧行 SET idempotency_key = key \|\| ':expired'` | 唯一槽位释放（`order-001` 和 `order-001:expired` 不冲突），旧行和历史**原封不动**，且 `:expired` 后缀本身就是可读的标记：运维一眼看出「这个 key 已被重新使用过一次」 |

修法二唯一的「代价」是 key 字段可能出现 `:expired` 后缀——查询时按前缀匹配即可，无实际影响。修完后我用 `test_idempotency_expired_outside_window` 把「旧行保留 + key 变为 `old-1:expired` + 新任务正常创建」三点全部锁定。

### 一个值得记录的教训

这类缺陷的根源是：**schema 的约束是「全称命题」，业务语义是「有时限的命题」**。冻结契约时两者表面一致（都叫「幂等唯一」），实现期才显形。这也反向验证了「小步 + 测试先行」的价值——它在第 1 步就被抓住，而不是上线后变成偶发的 500。

## 背景：`idempotency_key` 是干什么用的

想象业务方（比如广告系统）要通知供应商「用户 123 注册成功了」。业务方发出请求后，**网络可能超时——业务方不知道我们收没收到**。稳妥的做法是：过几秒再发一次同样的请求。

问题是：如果其实第一次已经收到了呢？那就会创建**两个重复的通知任务**，供应商被通知两次。

`idempotency_key` 就是解决这个的「防重贴标签」：业务方给同一次事件贴同一个标签（如 `order-001`）。我们的系统看到重复标签，就知道「这是重发，不是新事件」，直接把第一次的 task_id 还给业务方，不建新任务。

## 背景：两个「规则」各自是什么

系统里有**两个地方**在管这个标签，规则不一样：

**规则 A —— 数据库的 UNIQUE 约束**（写在冻结的 schema.sql 里）：

```sql
idempotency_key TEXT UNIQUE
```

意思是：**全表所有行里，这个标签不允许重复。不管多旧的行，占了这个标签，别的行就不能再用。** 数据库不懂什么叫「24 小时」，它只看标签有没有被人用过。

**规则 B —— 代码的 24h 窗口判定**（写在受理接口里）：

> 「24 小时**以内**的重复标签 → 返回旧任务；24 小时**以外**的重复标签 → 视为新请求，正常创建新任务。」

这是 stage2 定点 7 的语义：防重贴标签只保鲜 24 小时，过了保鲜期，同一个标签可以再用。

## 缺陷：两个规则在 24 小时后打架

看这个时间线（这就是测试抓出来的崩溃现场）：

```
第 0 小时
  业务方提交标签 order-001 → 任务 A 创建成功
  → 数据库里，order-001 这个标签被任务 A 占住了（规则 A 生效）

第 25 小时（超过 24h 保鲜期）
  业务方又提交标签 order-001（比如真要再通知一次）
  → 代码按规则 B 判定：25h > 24h，标签已过期 → 「可以创建新任务！」
  → 代码执行 INSERT，想插入一个标签同样是 order-001 的新行
  → 数据库按规则 A 拦下：这个标签已经被任务 A 占着，禁止！
  → 抛出 IntegrityError，接口 500 崩溃
```

一句话总结缺陷：**代码说「这个标签可以再用」，数据库说「这个标签永远只能用一次」**——两个判定者对「过期」的理解不一致。代码带了 24 小时的条件，数据库的约束没有任何时间概念。

更隐蔽的地方在于：**这个缺陷在正常测试里不会暴露**。前 24 小时内所有操作都正常（窗口内命中→返回旧任务；窗口内新 key→正常创建）。只有「同一个标签隔了一天后再次提交」这一种路径会崩——典型的边界条件 bug。

## 修复：让两个规则重新对齐

既然数据库的 UNIQUE 约束（冻结契约，不能改）要求「标签全表唯一」，那就必须在代码里**插入新行之前，把旧任务占的标签腾出来**。做法是给旧任务的标签加个后缀：

```
任务 A 的标签：order-001        →  改成：order-001:expired
                                          ↑ 标记「已被重新使用过」
新提交的 order-001              →  现在可以正常插入，不撞 UNIQUE
```

腾位置有两种方式，我当时先写了错误的那种：

- ❌ **把旧任务整行删掉**——标签是腾出来了，但任务 A 和它全部的投递历史记录也一起消失了。如果任务 A 曾投递失败、运维正要查它为什么失败——证据没了。你在 stage3 刚刚因为我砍掉历史表而驳回过我，我又差点犯同样的错，所以写完立刻自我否决。

## 24h 窗口是从哪来的

这是**我在 stage2 提出的设计，当时你确认通过**（定点 7）。它的来源是我套用了业界惯例——支付网关（如 Stripe）的 idempotency key 就是 24h 过期制。但「业界惯例」背后有个我们**不存在**的前提：

> Stripe 场景：key 是调用方每次请求**随机生成**的（一个 UUID 代表「这一次尝试」），key 空间无限大、永不复用，24h 过期纯粹是**清理存储**的运维考量。

而我们的场景完全不同：key 的用途是标识**业务事件**（`order-001` 这种业务 ID），不是标识「某一次 HTTP 尝试」。业务事件 ID 天然全局唯一，而且事件只会发生一次。

## 为什么「永久唯一」才是符合常理的

把两种语义的失败模式摆在一起对比，结论很清楚：

| 场景 | 24h 窗口制 | 永久唯一制 |
|---|---|---|
| 同事件 24h 内重发 | ✅ 去重正确 | ✅ 去重正确 |
| 同事件隔天重发（网络原因等） | ❌ **当成新请求 → 供应商被通知两次** | ✅ 返回旧 task，去重正确 |
| 调用方错误复用 key 发新事件 | 隔天后新事件能进去 | 返回旧 task（调用方会发现异常） |

我们系统的投递语义是**至少一次**——设计哲学本来就是「宁可重复不可丢失」。窗口制却在入口处主动制造「隔天重复投递」，**和自己的核心语义打架**。永久唯一制下，唯一的行为规则是：「同 key = 同事件，永远去重」，简单、可预测、和数据库的 UNIQUE 约束**天然一致**——上一轮那个缺陷的存在本身，就是「语义拧巴」的症状：语义拧巴的地方，代码一定拧巴。
