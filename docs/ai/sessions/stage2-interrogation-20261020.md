# 第 2 阶段：需求审讯（stage2-interrogation-20261020）

## 目的 / 结论 / 依据

- **目的**：把需求中的模糊点逐条逼出明确答案，形成可冻结的需求定点清单。
- **结论**：8 项定点 + 1 项接入工具全部经人类确认（含 3 项经追问后澄清/修订）。
- **依据**：作业原文需求描述；stage1 已确认的技术栈与边界；审讯过程中的多轮问答记录。

## 定点清单（人类确认，2026-10-20）

| # | 议题 | 定稿结论 | 判断依据 |
|---|---|---|---|
| 1 | 投递成功判定 | HTTP 状态码 2xx = 送达；不跟随 3xx 重定向；响应体不读取不存储 | 「业务方不关心返回值」豁免的是业务方（人类追问后澄清）；判断职责转移到本服务，看状态码是「可靠送达」的前提 |
| 2 | 4xx 处理 | 4xx 不重试，直接标 `dead`；仅 5xx/超时/连接错误重试 | 请求本身错误时重试同样字节只会得到同样结果 |
| 3 | 重试策略 | 指数退避 base=30s、factor=2，最多 7 次尝试（1+6），总窗口约 1 小时，超限标 `dead`；参数走配置文件 | base/factor 为行业惯例+业务特征的工程默认值（AI 声明非实测调优）；前密后疏兼顾瞬时抖动与长期故障；jitter 第一版不做（单 worker 无惊群），并发化后为必选 |
| 4 | HTTP 超时 | 连接 5s + 读 10s；超时归入「未知结果」按失败重试 | 保护自身 worker 线程不被无限等待挂死；超时即「不知道成没成功」，是至少一次语义的来源之一（人类追问连接/读两阶段后确认理解） |
| 5 | 状态机 | `pending → delivering → done / retrying → dead` | `delivering` 中间态用于崩溃恢复，是 SQLite 方案下至少一次成立的关键 |
| 6 | 供应商差异 | 服务端不做模板/适配器，业务方提交最终形态 `url+method+headers+body` | 适配逻辑留在最懂供应商格式的业务方侧，本服务保持纯投递管道 |
| 6+ | 接入工具 | `scripts/submit_notification.py`（标准库 urllib+argparse）：本地校验 → 提交 → 返回 task_id（人类提出「提供表单/脚本辅助填写」，AI 收敛为 CLI 工具并放弃 Web 表单方案） | 客户端工具不进服务端，失败模式为零；内部服务调用方是程序员，CLI 是正确量级 |
| 7 | 幂等提交 | 可选 `idempotency_key`，24h 内相同 key 返回首次 task_id | 至少一次语义下无入口幂等会放大下游重复；成本仅一个唯一索引 |
| 8 | 查询接口 | `GET /tasks/{id}` + `GET /tasks?status=dead` 两个最小接口 | 无查询能力则死信无人能处理，「长期不可用策略」停在纸面 |

## 明确不做清单（stage2 补充）

鉴权、多租户、优先级队列、模板系统、Web 控制台、jitter、响应体解析。

## 审讯中的理解修正记录

- 人类就「下游没有返回值」提出疑问 → AI 澄清：需求原文「业务系统不需要关心返回值」主语是业务系统，读取状态码的职责转移给本服务；只看状态码、不解析响应体。
- 人类就第 4 点超时提出疑问 → AI 以连接/读两阶段图解说明；确认超时保护的是自身可用性。
- 人类就重试参数 base/factor 提问 → AI 声明：非数学推导，为惯例默认值，未经真实流量验证，故入配置文件待上线后按 dead 任务失败原因分布调优。

## 遗留

- MQ 演进论证 → 后续阶段（改判条件见 stage1）。
- 会话导出方式（Q3）、deadline（Q5）→ 不阻塞，对应阶段再问。
- 契约起草 → 第 4 阶段。
