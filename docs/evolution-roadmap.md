# 演进路线图：从 MVP 到百亿/千亿量级的稳定投递架构

> **目的**：回答「数据量演进到几十亿、百亿、千亿规模时如何保证稳定投递」。
> **结论**：四级演进——SQLite 单机 → PostgreSQL 分区 → 分片 + Kafka 骨干 + 投递集群 → 单元化 + 分层存储。每级由**量化触发指标**驱动，禁止预支。
> **依据**：stage1 已确立的失效边界（存量百万/活跃万/写入百每秒）；本文件的量级推演明确标注「推断」或「业界已知实践」。

---

## 0. 先校准问题：规模数字的含义

讨论「几十亿」前必须先问：是**存量**（历史任务总数）还是**吞吐**（每天新增投递）？两者的瓶颈完全不同：

| 口径 | 几十亿意味着什么 | 主要瓶颈 |
|---|---|---|
| 存量 10⁹~10¹¹ | 表太大、索引太深、存储太贵 | 存储经济性、冷热分层 |
| 吞吐 10⁹/天 ≈ 1.2万/s | 写入与投递并发 | 写入路径、投递集群、供应商限流 |

下文按「存量」为主线设计（与本题上下文一致），每级同时标注吞吐含义。**稳定投递**在此规模下的定义也随之变化：从「不丢」演进为「不丢 + 不超时违约（SLO）+ 不拖垮供应商 + 单位成本可控」。

## 1. 现状基线（Stage 0，已完成）

SQLite 单机 + 轮询 + 单 worker。边界：存量百万、活跃任务万、写入百/s。
**此级不需要任何动作**——但为演进预留的三个设计此刻就在生效：store 层隔离（换存储只动一个模块）、任务表数据模型（近原样迁 PG）、attempt 历史模型（近原样迁列存）。

## 2. Stage 1：PostgreSQL 分区（存量 10⁶ → 10⁸，写入 10² → 10³/s）

**瓶颈**：SQLite 单写锁 + 单文件体积 + 无并发读扩展。

**架构动作**：
```
替换：SQLite → PostgreSQL 15+
 ├─ tasks 表按 created_at RANGE 分区（月/周），completed 分区到期归档
 ├─ LISTEN/NOTIFY 替代轮询：受理端写入后 NOTIFY，worker 阻塞等待唤醒
 │   （推送语义达成，投递延迟从 ~0.5s 降到 ms 级；NOTIFY 丢失由
 │    1s 兜底轮询覆盖——推拉结合，NOTIFY 只做加速不做保证）
 ├─ worker 从线程改为多进程（PG 连接是进程安全的），横向加进程即扩容
 └─ task_attempts 照搬（PG 下此量级列存尚不必要）
```

**保留不变**：状态机、退避参数、快照+rerender 语义、at-least-once、幂等键。应用层唯一改动在 store.py 与 worker 的取任务入口——stage1 押注的隔离层在此兑现。

**触发升级指标（任一即启动 Stage 2 设计）**：
- 单分区表写入 > 5000/s（PG 单实例写墙，推断值，以实测为准）
- tasks+attempts 总量 > 2TB（单实例存储运维痛阈值）
- 投递集群需要 > 1 台机器承载（CPU/连接数）

**代价**：获得推送与并发写，付出一个 DBA 级组件的运维（备份/PITR/主从）。

## 3. Stage 2：分片 + Kafka 骨干 + 无状态投递集群（存量 10⁸ → 10¹⁰，吞吐 10³ → 10⁴/s）

**瓶颈**：单 PG 实例的写入墙；轮询/推送模型在多机下的任务分发公平性；重试风暴对供应商的反压。

**架构动作**——这是最大的一次结构变化，核心思想：**把「受理」与「投递」之间的同步依赖断开，队列成为唯一骨干**：

```
                    ┌─────────────────────────────────────┐
 受理层（无状态）    │  Kafka：notification-events          │
 N 实例 ──────────→ │  分区键 = vendor_id（供应商亲和）      │
  │ 本地事务写 outbox│  分区数 = 供应商数 × 并行度            │
  └─ outbox relay──→ └──────────────┬──────────────────────┘
     （轮询 outbox 表）              │ consumer group
                                    ▼
                    ┌─────────────────────────────────────┐
                    │ 投递集群（无状态容器 × N）             │
                    │  每 consumer 一个供应商分区 → 天然     │
                    │  串行 + 限速，不惊群不超卖             │
                    └──────────────┬──────────────────────┘
                                   │ 失败 → retry topic（退避分层）
                                   │        retry-1m / retry-10m / retry-1h
                                   │ 耗尽 → dead-letter topic
                                   ▼
                    PostgreSQL（任务态）+ Kafka（流转）双写由
                    Transactional Outbox 保证原子（ADR-001 时代已论证的
                    模式，此刻正式启用）
```

**关键设计决策**：

1. **Transactional Outbox 正式启用**（stage1 论证过它此刻才值得付出）：受理 = 本地事务（tasks + outbox 同库），relay 单向推送 Kafka。这解决了「DB 写成功但 MQ 发失败」的原子性，是此规模下不可绕过的代价。
2. **Kafka 分区键 = vendor_id**：同一供应商的任务落在同一分区、同一 consumer——天然获得**每供应商全序 + 天然限速点**。供应商限流在 consumer 内做令牌桶即可，不需要分布式限流器。
3. **重试退避从「字段」升级为「拓扑」**：retry-1m/10m/1h 三级 topic 替代 next_attempt_at 字段。代价是失败路径复杂化；收益是重试流量与主流量物理隔离，重试风暴不会饿死新任务（现在是同一张表抢 LIMIT 1）。
4. **幂等键去重**升级：受理侧仍查 tasks 表（此时按 vendor_id 分库），另加 bloom filter/Redis 前置挡重复查询（优化非正确性依赖）。
5. **attempt 历史**迁 ClickHouse（列存）：10¹⁰ 任务 × 平均 1.5 次尝试 = 1.5×10¹⁰ 行历史，行存 DB 的存储成本不可接受；运维查询是低频分析型，列存天然匹配。写入走 Kafka 副 topic 异步落。

**触发升级指标**：
- 单 vendor 分区积压持续增长（供应商限速是硬墙，加机器无效——见 Stage 3 的多通道）
- 跨区域供应商延迟成为主导（投递 P99 受物理距离支配）
- 存储成本 / 单条投递成本进入成本红线（历史数据占 80%+）

**代价**：系统从「一个进程能看懂」变成「一套数据流水线」——**失败模式数量翻了一个数量级**，必须同步建设：全链路 trace（task_id 贯穿）、Kafka lag 告警、chaos 演练（broker 宕机/consumer 卡死/outbox 积压）。这一级最大的风险不是技术而是**可推理性的丧失**，用可观测性买回来。

## 4. Stage 3：单元化 + 分层存储 + 多通道路由（存量 10¹⁰ → 10¹¹+，吞吐 10⁴ → 10⁵/s）

**瓶颈**：跨区延迟与爆炸半径；单一 Kafka 集群容量；供应商侧的物理墙（对方每秒只接受 X 个请求，我们再快也没用）。

**架构动作**：

1. **单元化（cell-based）**：按 vendor_id 哈希切分成独立「单元」，每单元 = 自己的受理实例 + Kafka 集群 + 投递池 + PG 分片。单元间零共享，单单元故障爆炸半径 = 1/N。路由层（极薄）按 vendor 把流量导入对应单元。这是 10¹¹ 规模业界已知的标准解法（支付/消息平台的 cell 架构）。
2. **多通道路由**：对「限流墙」供应商建立多通道——不同出口 IP/区域/协议（若供应商提供多接入点）并行消化；配合**配额协商机制**：与供应商签订速率配额，我方按配额精确投放并暴露「队列深度换速度」的权衡给业务方（告诉他们这个供应商的 SLA 就是 10 分钟级，而不是假装能秒到）。
3. **分层存储**：热数据（7 天内活跃任务）在 PG/单元库；温数据（已 done/dead 任务）压缩归档对象存储；冷数据（attempt 历史）ClickHouse TTL 降级 → 对象存储 parquet。**存量几百亿的关键不是「存得下」而是「查得动、买得起」**。
4. **SLO 化运营**：投递不再承诺「尽力而为」，按 vendor 分级 SLO（金/银/铜：P99 1min/10min/1h），容量规划按 SLO 反推——队列深度 × 供应商配额 = 排队时间，排队时间 > SLO 即自动扩容或降级告警。
5. **混沌常态化**：此规模下「稳定」不再靠设计保证，靠**演练证明**——每月注入 broker 失联/供应商雪崩/分区倾斜/证书过期故障，SLO 违约率是唯一验收标准。

**代价**：一个平台团队级的运维组织；每条投递的基础设施成本成为一等设计约束（千亿量级下每条省 0.1 分钱 = 千万级成本）。

## 5. 贯穿所有级别的四条不变量

无论架构怎么变，这些从 MVP 带出来的原则**一级都不放松**：

1. **至少一次 + 下游幂等**：规模越大越不能升级为 exactly-once（那需要下游配合分布式事务，跨公司不可能）。语义从第一天生死与共。
2. **投递行为可追溯**：快照（最终请求字节）在任何一级都必须可查——从 tasks 表列 → PG 表 → 对象存储归档，形态变、能力不变。**千亿规模下一次供应商纠纷的取证价值远超存储成本**。
3. **失败可见**：从 last_error → task_attempts 表 → ClickHouse + trace，形态在变，「每条通知发生了什么可回答」不变。
4. **每级失效边界预先写明**：本文档每个 Stage 的触发指标就是这个原则的延续——**演进由指标触发，不由焦虑触发**。

## 6. 诚实声明

- Stage 2/3 的容量数字（5000/s 写墙、2TB 痛点等）是**基于业界已知实践的推断**，未经本系统实测；真正的数字必须在 Stage 1 上线后用压测校准。
- 本路线图是**决策框架**而非施工图——每一级的详细设计都应该在**触发指标逼近时**重新做一次对抗（就像 stage3 那样），因为届时会有此刻不存在的约束（团队规模、预算、供应商契约变化）。
- 反过来这句也成立：如果业务十年都停在 Stage 0 的量级，这份路线图的价值就是让人**安心地不做任何事**。
